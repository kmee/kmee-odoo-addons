Issue and follow boletos and Pix charges in several Brazilian banks
through `brbank <https://github.com/kmee/brbank>`__, a Python library
with one adapter per bank. This module is the Odoo face of the library:
one generic payment provider (``code = brbank``) and one provider record
per bank, so a new bank is data and a credentials screen, not a new
module.

Banks delivered as providers (all disabled until configured):

- Boleto: Banco Inter, PinBank, Sicoob, Sicredi, Banco do Brasil, Itaú,
  Bradesco, Santander, BTG Pactual, C6 Bank, Banrisul, Unicred, Caixa
  and Safra.
- Pix (BACEN API, ``/cob`` and ``/cobv``): Banco Inter, Banco do Brasil,
  Sicoob, Sicredi, Itaú, Bradesco, Santander and Efí.

What the module does:

- One bank title per open installment of the invoice, each transaction
  tied to its installment (``move_line_id`` of
  ``l10n_br_payment_boleto``): issuing again never charges twice, and
  paying out of order settles the right installment.
- Transaction states follow the canonical status of the bank: pending
  registration -> pending, registered -> authorized, settled -> done,
  written off -> canceled, rejected -> error. A transaction is only
  settled after the bank is queried: a webhook never settles anything by
  itself.
- Digitable line, bar code, Pix copy and paste and TXID on the
  transaction, on the invoice PDF and in the customer portal.
- Bank instructions (due date extension, rebate, protest, credit bureau
  report, write-off) as records with the answer of the bank, offered
  only when the bank declares the capability.
- A generic webhook per provider, protected by a secret token, that
  stores the events and answers at once; the events are processed by a
  cron triggered immediately, which queries the bank.
- A reconciliation cron for every brbank provider, as the safety net of
  the webhooks.
- Credentials readable only by system administrators; certificates go to
  the library only in memory; logs and stored bank answers are masked by
  the library (no name, document, address or PDF of the payer).

The library is asynchronous; the module calls it through a single bridge
that runs each call in a dedicated, short lived event loop.

Configuration
=============

1. Install the ``brbank`` Python library in the Odoo environment
   (``pip install "brbank>=0.0.3"``). It needs Python 3.10 or later.
   Version 0.0.3 is the minimum: it brings the adapters of Itaú,
   Bradesco, Santander, BTG Pactual, C6 Bank, Banrisul, Unicred, Caixa
   and Safra (the manifest only names the package, so the version is not
   checked at install).
2. Go to *Invoicing > Configuration > Payment Providers* and open the
   provider of the bank (for instance *Sicoob (Boleto)* or *Pix Itaú*).
3. In the *Credentials* tab:

   - the bank adapter (and the Pix profile) are already set by the data;
   - fill the credentials the adapter asks for (client id and secret,
     API user and password, certificate and private key in PEM, Pix
     key). Only the fields the adapter uses are shown;
   - click *Fill settings template* and complete the JSON of *Extra
     Settings* (agreement, wallet, client number and so on) and *Extra
     Secrets* (developer key, API key and so on). *Settings Keys* lists
     every key with its type, which ones are required and which ones are
     secret;
   - if the bank has a webhook, register the *Webhook URL* at the bank.
     *Rotate webhook token* issues a new URL and stops the old one at
     once.
   - keys typed as a function in the library (``gerar_nosso_numero``,
     ``ao_renovar_refresh_token``) never go in the JSON: the provider
     serves them (see below).

4. Set the provider to *Test Mode* (bank sandbox) or *Enabled*
   (production) and choose its journal in the *Configuration* tab. The
   provider refuses to leave *Disabled* while a required key is missing.
5. In the payment mode (*Invoicing > Configuration > Payment Modes*),
   tick *Generate boletos on invoice?* and choose the provider. The
   payment mode shows what the bank supports.

Notes per bank:

- **BTG Pactual**: the API only accepts tokens of the authorization code
  flow, done once at the BTG Id outside Odoo. Paste the refresh token it
  gives in *Refresh Token*. The bank may return a new refresh token at
  each renewal and invalidate the old one: the provider saves it at
  once, in a database transaction of its own, so an error or a rollback
  of the operation never loses it. A refresh token unused for more than
  10 days expires and the consent must be done again. Use each BTG
  credential in one database only. Fill ``dias_expiracao`` (days after
  the due date until the title expires), or the bank refuses titles
  without an automatic write-off term.
- **Caixa**: there is no public test environment, so the provider
  refuses the *Test Mode*. Enable it and validate with a title of low
  amount. ``documento_beneficiario`` is a secret key (*Extra Secrets*).
- **C6 Bank**: the Pix key must be a random key (EVP); the bank silently
  issues a boleto without Pix with any other kind.
- **Itaú**: ``bolecode`` (hybrid boleto) is on by default and needs the
  Pix key.
- **Santander**: the Pix key needs ``tipo_chave_pix`` (EMAIL, CPF, CNPJ,
  CELULAR or EVP); ``workspace_id`` is the billing workspace created at
  the bank.
- **Bradesco**: ``documento_beneficiario`` is a secret key (*Extra
  Secrets*).
- **Banrisul**: the provider sends the 8 free digits of the nosso numero
  and the library adds the check digits.
- **Unicred**: ``api_key`` and the two webhook keys go in *Extra
  Secrets*.
- **Safra**: the bank declares no capability (no write-off, instruction,
  PDF nor webhook): titles are followed by the reconciliation cron only.

Nosso numero: for the banks where the issuer chooses it (Banco do
Brasil, Itaú, Santander, Banrisul, Caixa and Safra) the provider creates
its own sequence (*Nosso Numero Sequence*) at the first title, starting
after the numbers already registered by it. The number is taken before
the first call to the bank and kept on the transaction (*Nosso Numero
Sent*), so a retry sends the same one, and a number is never given
twice. When the sequence passes the digits of the bank (Itaú 8, Banrisul
8, Safra 9, Banco do Brasil 10, Santander 12, Caixa 15), the
registration stops with an error instead of cutting the number: agree
with the bank on a new wallet or agreement.

Only users of *Administration / Settings* see and edit the credentials.
The webhook token travels in the URL: mask it in the logs of the reverse
proxy.

Crons:

- *Boleto brbank: reconcile titles with the banks*, every 30 minutes,
  the same period of the Inter and PinBank modules, so the delay between
  payment and settlement does not get worse. Lengthen it only when the
  webhook of every bank in use is validated in production.
- *Boleto brbank: process bank webhook events*, triggered by every
  webhook call and every 10 minutes as a fallback.

Usage
=====

Issuing:

- Post a customer invoice whose payment mode generates boletos with a
  brbank provider: one transaction per open installment is created and
  registered at the bank. *Generate boletos* again only issues the
  installments without a live title.
- If the bank is unavailable, the transaction stays in draft with the
  reason and the reconciliation cron registers it later with the same
  idempotency key. If the bank refuses the data, the posting stops with
  the reason, naming the missing customer fields.
- The invoice PDF and the portal show, per open title, the due date, the
  amount, the digitable line and the Pix copy and paste (with its QR
  code). The portal also offers the boleto PDF when the bank provides
  one.

Following up, in the transaction:

- *Check at the bank* reads the title back and applies its status. The
  *Capture* button of ``payment`` does the same, and *Void* writes the
  title off.
- *Bank instruction* sends a due date extension, a rebate, a protest or
  a credit bureau report; *Write off at the bank* cancels the title. The
  buttons only show when the bank declares the capability; a command the
  bank refuses stays recorded as rejected, with the reason.
- For BTG Pactual, the *Refresh Token* of the provider changes by itself
  after the calls to the bank: the provider keeps the last token the
  bank returned.
- *Invoicing > Customers > Boleto Instructions* lists every instruction,
  and *Invoicing > Configuration > Payments > Bank Webhook Events* every
  event received (managers only).

Return files (CNAB): a module that reads a return file of an account
that also uses the API can call
``payment.transaction._brbank_notify_cnab_occurrence( nosso_numero, company)``:
the transaction is found by its nosso numero and read back from the
bank, so the file and the API never settle the same title twice.

Moving from ``l10n_br_payment_boleto_inter`` or
``l10n_br_payment_boleto_pinbank``:

1. Configure the brbank provider of the same bank (*Banco Inter
   (Boleto)* or *PinBank (Boleto)*) with the credentials of the old
   provider.
2. In the payment mode, replace the old provider by the brbank one in
   *Payment provider*: this single field links the payment mode to the
   bank.
3. New invoices are issued through brbank. The titles issued before stay
   with the old provider and its cron until they are paid or written
   off; uninstall the old module only after that.

Known issues / Roadmap
======================

- **No adapter of the brbank library has been validated in a bank
  sandbox yet** (``validado_sandbox = False`` in all of them). Inter and
  PinBank were ported from modules running in production, the others
  were built from public documentation. The provider form and the
  payment mode warn about it. Test each bank with low amounts before
  production.
- The minimum version of brbank is 0.0.3 (adapters of Itaú, Bradesco,
  Santander, BTG Pactual, C6 Bank, Banrisul, Unicred, Caixa and Safra),
  not on PyPI yet; 0.0.2, on PyPI, runs on Python 3.10 but has the first
  five banks only. The manifest names the package without a version (a
  specifier there breaks the import check), so the minimum is not
  enforced at install.
- The registration runs in the transaction that posts the invoice. If
  that transaction is rolled back after the bank answered, the bank
  keeps the title; the next attempt sends the same idempotency key (Pix
  answers ``Duplicado`` and the title is read back), but a boleto bank
  that does not deduplicate by our reference may keep an orphan title.
  The nosso numero is kept on the transaction, so a retry of the same
  transaction sends the same number; a transaction undone by the
  rollback takes a new number on the next attempt (the sequence never
  gives a number twice).
- Webhooks are only parsed for the banks whose adapter declares them
  (Inter, Sicredi, BTG Pactual, C6 Bank, Unicred and the Pix profiles);
  the others rely on the reconciliation cron.
- The digits of the nosso numero of each bank are a map in the module
  (``NOSSO_NUMERO_DIGITS``), checked by a test against the adapters that
  take ``gerar_nosso_numero``; the library does not publish them in a
  uniform way.
- BTG Pactual: the authorization code flow (consent at the BTG Id) is
  done outside Odoo. Two calls renewing the same refresh token at the
  same time (two workers) may leave one of them with a token the bank
  already replaced.
- Caixa has no test environment: the provider cannot use the test mode.
- The webhook events are processed by ``ir.cron`` with an immediate
  trigger, not by ``queue_job``, so the module adds no dependency; move
  to ``queue_job`` if a bank sends large volumes.
- The CNAB bridge is a hook (``_brbank_notify_cnab_occurrence``): no
  return file module calls it yet.
- The brbank providers are left out of the online checkout: the redirect
  and token flows of ``payment`` are not implemented for them.
- The credentials are stored in the database, restricted to the settings
  group; a vault (Vault, KMS) is a decision still open.
- The reconciliation cron queries each open title; banks with batch
  queries or movement statements could be read in one call per account.
- No alert yet for certificates close to expiry.
- The provider records use the module icon; the logos of the banks are
  not shipped.
